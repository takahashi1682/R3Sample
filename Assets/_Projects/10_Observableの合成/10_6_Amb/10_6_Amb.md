# 10_6. Amb

## この回で学ぶこと
- `Observable.Amb`が複数のストリームを「競争」させ、最初に値を出したものだけを採用する仕組みを理解する
- 一度勝者が決まった後は、負けたストリームの値が二度と使われないことを理解する
- Ambが他の合成オペレーターと異なり「値を混ぜたり組み合わせたりしない」特殊な合成であることを理解する

## 前提知識
- Observable / Subject / Subscribe の基本（0〜4の回）
- `OnNext` / `OnCompleted`を手動で呼び出してストリームの流れを確認する方法
- `AddTo(this)`によるリソース管理
- 10_1_Mergeの内容（「複数を混ぜる」Mergeとの対比で理解が深まります）

## 概念解説
Amb（Ambiguous＝「あいまいな」の略）は、これまでのMerge/Concat/Zip/ZipLatest/CombineLatestとは毛色が異なる合成オペレーターです。他のオペレーターが「複数のストリームの値をどうにかしてまとめて使う」のに対し、Ambは**複数のストリームを競争させて、最初に値を出した1本だけを採用し、残りは完全に無視する**という動きをします。

イメージとしては、よーいドンの徒競走です。ストリーム1とストリーム2が同時にスタートし、どちらか先に値を出した方（＝先にゴールした方）だけが「採用ストリーム」として選ばれます。一度勝者が決まったら、負けた方のストリームにその後どれだけ値が流れても、二度と結果には反映されません。

```
subject1: -----A-----C--->
subject2: --B-----D------->

Amb     : --B-----D------->   （subject2が先に値を出したので、以降はsubject2だけを採用）
```

- 最初に値（`OnNext`）を出したストリームが「勝者」になる
- 勝者が決まった時点で、他のストリームの購読は打ち切られる（それ以降値を出しても無視される）
- 以降のAmb全体の`OnNext`・`OnCompleted`は、すべて勝者ストリームのものだけが使われる

他のオペレーターとの違いは明確です。Mergeは「両方の値をそのまま混ぜる」、Zip/CombineLatestは「両方の値を組み合わせる」のに対し、Ambは「どちらか一方だけを選び、もう片方は最初から存在しなかったことにする」という点で、まったく異なる目的のオペレーターです。例えば「複数のサーバーに同時に問い合わせて、一番早く返ってきたレスポンスだけを使いたい」といった場面で活躍します。

## シーンの操作方法
1. `10_6_Amb`シーンを開いてPlayします。
2. Consoleを確認し、`_subject2.OnNext("Subject2")`が先に呼ばれるため、`next.Subject2`が出力されることを確認してください。
3. 直後に呼ばれる`_subject1.OnNext("Subject1")`は、ログに一切出力されないことを確認してください。
4. 2回目の`_subject2.OnNext("Subject2")`は引き続き出力され、2回目の`_subject1.OnNext("Subject1")`は無視され続けることを確認してください。
5. `_subject2.OnCompleted()`が呼ばれた時点で`completed.`が出力され、その後の`_subject1.OnCompleted()`は何の影響も与えないことを確認してください。

## コード解説
```csharp
Observable
    .Amb(
        _subject1,
        _subject2
    ).Subscribe(
        x => Debug.Log("next." + x),
        onCompleted: _ => Debug.Log("completed.")
    ).AddTo(this);
```
`Observable.Amb`に渡した複数のストリームは、どれも最初は同時に購読された状態になります。しかし、実際に値を流すまでは「まだどちらが採用されるか決まっていない」状態です。

```csharp
// それぞれのSubjectにデータを流す
// Ambは最初に値を発行したSubjectのみを購読し続ける（この場合はsubject2）
_subject2.OnNext("Subject2"); // next.Subject2
_subject1.OnNext("Subject1"); // 流れない
```
`_subject2`が先に`OnNext`を呼んだ時点で、Ambは「勝者は`_subject2`」と確定します。この確定によって`_subject1`の購読は打ち切られるため、直後の`_subject1.OnNext("Subject1")`はもう誰にも届かず、ログには出力されません。

```csharp
_subject2.OnNext("Subject2"); // next.Subject2
_subject1.OnNext("Subject1"); // 流れない
```
勝者が決まった後は、何度呼び出しても同じ結果になります。`_subject2`の値はそのまま流れ続け、`_subject1`の値は永久に無視されます。

```csharp
_subject2.OnCompleted(); // completed.
_subject1.OnCompleted();
```
勝者である`_subject2`が完了すれば、Amb全体もそのまま完了します。すでに購読が打ち切られている`_subject1`が後から`OnCompleted()`を呼んでも、Ambの結果には何の影響もありません。

## 実行結果の例
```
next.Subject2
next.Subject2
completed.
```
（`_subject1`側の`OnNext`・`OnCompleted`はどれもログに出力されません）

## よくあるつまずきポイント
- Mergeと混同して「両方の値が出力される」と思い込みやすいですが、Ambは**最初に値を出した1本だけ**を採用し、もう片方は最初から無視されます。値が混ざることはありません。
- 「勝敗はストリームを渡した順番（引数の順）で決まる」と誤解しないようにしましょう。実際に決まるのは「どちらが先に値（`OnNext`）を出したか」であり、コード上の記述順ではありません。もし引数の順を逆にして`_subject1`が先に値を出せば、`_subject1`が勝者になります。
- 負けたストリームの`OnCompleted()`や以降の`OnNext()`が結果に一切影響しない点も、初めて見ると見落としやすいポイントです。
