# 3-1. 値の更新を監視する

## この回で学ぶこと
- `ReactiveProperty<T>` を実際に宣言し、値の変化を `Subscribe` で監視する方法
- Inspector に表示する宣言方法（`SerializableReactiveProperty<T>`）と表示しない宣言方法の違い
- 外部に公開するときに `ReadOnlyReactiveProperty<T>` を使う理由
- `AddTo(this)` によるライフサイクル管理（自動 Dispose）の基本

## 前提知識
- 3-0 で学んだ ReactiveProperty の概念（値＋自動通知）
- Unit1〜2 の `Observable.Interval`、`Subscribe`、`AddTo` の使い方
- MonoBehaviour の `Awake`/`Start` の実行順序

## 概念解説
前回は ReactiveProperty のイメージだけを説明しましたが、今回は実際にコードで使ってみます。

まず、コード中のクラス名に注目してください。値を発行する側のクラスは `ReactiveProperty` ではなく **`SampleReactiveProperty`** という名前になっています。これは、R3 ライブラリ自身が `ReactiveProperty<T>` というクラスをすでに持っているためです。もし自分のクラス名を `ReactiveProperty` にしてしまうと、同じ名前がコード内で衝突し、どちらの `ReactiveProperty` を指しているのか分かりにくくなってしまいます（名前の「影」に隠れてしまうことを「シャドーイング」と呼びます）。**ライブラリが提供している型と同じ名前を自分のクラスに付けない**というのは、実務でも重要な習慣なので覚えておきましょう。

次に、2種類の宣言方法を見比べます。

```csharp
[SerializeField] private SerializableReactiveProperty<int> _count1 = new(0);
public ReadOnlyReactiveProperty<int> Count1 => _count1;

private readonly ReactiveProperty<int> _count2 = new(0);
public ReadOnlyReactiveProperty<int> Count2 => _count2;
```

`_count1` は `SerializableReactiveProperty<int>` で宣言されているため、Inspector 上に値が表示され、Play 中でも直接書き換えることができます。一方 `_count2` は普通の `ReactiveProperty<int>` なので、Inspector には表示されず、コードの中だけで完結する値になります。「Inspector で確認・デバッグしたい値」か「外から触られたくない内部専用の値」かで使い分けるのがポイントです。

また、どちらも外部に公開するプロパティ（`Count1`, `Count2`）の型は `ReadOnlyReactiveProperty<int>` になっています。これは、他のスクリプトから `.Value = 999` のように勝手に書き換えられてしまうのを防ぐためです。値を変更できるのは `SampleReactiveProperty` 自身だけにして、外部には「読み取り専用の窓口」だけを見せる、という設計です。

## シーンの操作方法
1. Hierarchy の `Scripts` オブジェクトを選択した状態で Play します。
2. Inspector を見ると、`Sample Reactive Property` コンポーネントの `Count 1` の値が1秒ごとに増えていくのが確認できます（`_count2` は private なので Inspector には表示されません）。
3. Console を開き、`SampleObserver` が出力する `Count1: n` と `Count2: n` のログが1秒ごとに増加していくことを確認してください。
4. 発展課題：Play 中に Inspector 上の `Count 1` の値を直接ドラッグ／入力して書き換えてみましょう。Interval を待たずに、その場で Console に新しい値のログが出力されるはずです。これは「値が変わった瞬間に通知が飛ぶ」という ReactiveProperty の性質を、Inspector 経由でも体感できる操作です。

## コード解説
`SampleReactiveProperty.cs`
```csharp
private void Start()
{
    _count1.AddTo(this);
    _count2.AddTo(this);

    Observable.Interval(TimeSpan.FromSeconds(1))
        .Subscribe(_ =>
        {
            _count1.Value++;
            _count2.Value++;
        })
        .AddTo(this);
}
```
- `_count1.AddTo(this)` / `_count2.AddTo(this)`：ReactiveProperty 自身も `IDisposable` です。`this`（この MonoBehaviour）が破棄されるタイミングで一緒に Dispose されるように登録しています。登録し忘れると、GameObject が消えた後もイベントの購読が残り続けてメモリリークの原因になります。
- `Observable.Interval(TimeSpan.FromSeconds(1))`：1秒ごとに値を流す Observable を作成します。
- `.Subscribe(_ => { ... })`：Interval が値を流すたびに、`_count1.Value++` と `_count2.Value++` を実行します。この代入がトリガーとなって、それぞれの ReactiveProperty を購読している側に通知が飛びます。
- 最後の `.AddTo(this)` は `Subscribe` が返す購読（`IDisposable`）を破棄対象に登録するためのもので、上の2つの `AddTo` とは対象が異なる点に注意してください。

`SampleObserver.cs`
```csharp
private void Awake()
{
    _program1.Count1.Subscribe(count =>
    {
        Debug.Log($"Count1: {count}");
    }).AddTo(this);
    ...
}
```
- `_program1.Count1.Subscribe(...)`：`SampleReactiveProperty` が公開している `ReadOnlyReactiveProperty<int>` を購読しています。値が変わるたびにこのラムダ式が実行されます。
- `SampleObserver` は `Awake()` で購読を開始し、`SampleReactiveProperty` 側は `Start()` で `Observable.Interval` を開始しています。Unity の実行順序では基本的に全ての `Awake` が終わってから `Start` が呼ばれるため、値が動き出す前に確実に購読が完了しているという順序関係も意識しておきましょう。

## 実行結果の例
Play 開始直後の Console には、1秒ごとに以下のようなログが増えていきます。
```
Count1: 1
Count2: 1
Count1: 2
Count2: 2
Count1: 3
Count2: 3
...
```
Inspector の `Count 1` フィールドの数値も同じタイミングで増加します。

## よくあるつまずきポイント
- `SampleReactiveProperty` というクラス名を見て「なぜ ReactiveProperty という名前にしないのか」と疑問に思うかもしれませんが、これは R3 の `ReactiveProperty<T>` と名前が衝突するのを避けるためのリネームです。自作クラスに R3 の型と同じ名前を付けないようにしましょう。
- `_count2` が Inspector に表示されないことを「バグでは？」と思ってしまう学生がいますが、これは `SerializeField` を付けていない仕様通りの動作です。
- `AddTo(this)` を書き忘れても、シーンを止めるまでは一見動いているように見えてしまうため、その場で不具合に気づきにくい点に注意してください。
