# 30-6. 条件がTrueになるまで待機する

## この回で学ぶこと
- `UniTask.WaitUntil`を使って、「条件が満たされるまで待つ」処理を書く方法
- 条件を判定するための関数（ラムダ式）の渡し方
- 【重要】終わりが保証されない待機処理には、必ずキャンセル手段を用意しておくべき理由

## 前提知識
- 30-4・30-5で学んだ`CancellationToken`（`destroyCancellationToken`、`CancellationTokenSource`）
- C#のラムダ式（`() => ...`という書き方）を見たことがある程度でOK

## 概念解説
これまでは「3秒待つ」のように、待つ時間があらかじめ決まっている非同期処理を扱ってきました。しかし実際のゲームでは、「時間」ではなく「ある条件が満たされるまで」待ちたい場面がよくあります。たとえば「プレイヤーが特定のボタンを押すまで」「特定のアイテムを拾うまで」といったケースです。

これを実現するのが`UniTask.WaitUntil`です。`UniTask.WaitUntil(() => 条件)`のように書くと、渡した条件（関数）が`true`を返すまで、その場で待機してくれます。内部では毎フレームこっそり条件をチェックしにきているとイメージするとわかりやすいでしょう。

ここで注意したいのは、`WaitUntil`は「いつ終わるかわからない」待機処理だという点です。もし条件が永遠に`true`にならなかったら（たとえば、対応するボタンが二度と押されないまま画面が切り替わってしまった場合など）、この待機処理はいつまでも終わらず、待っているオブジェクトの参照をずっと持ち続けてしまいます。これはメモリリークの原因になり得ます。

だからこそ、このサンプルでは`cancellationToken: destroyCancellationToken`を渡しています。こうしておくことで、「条件が満たされる」か「オブジェクトが破棄される」かのどちらか早い方で待機が終わるようになります。終わりが保証されない待機処理には、必ず何かしらのキャンセル手段をセットで用意しておく、と覚えておいてください。

## シーンの操作方法
1. Playボタンを押します。
2. 何もしない状態ではログが出ないことを確認します（条件がまだ`false`のままです）。
3. 画面上のボタンを押すと、条件が`true`になり、Consoleに「条件が true になりました」というログが表示されることを確認してください。

## コード解説
```csharp
private bool _isTrue = false;

private async void Start()
{
    // _isTrue が true になるまで待機する（破棄されたら待機を打ち切る）
    await UniTask.WaitUntil(() => _isTrue, cancellationToken: destroyCancellationToken);

    Debug.Log("条件が true になりました");
}

public void OnClicked()
{
    _isTrue = true;
}
```
- `private bool _isTrue = false;`: これから満たしたい条件を表すフィールドです。
- `() => _isTrue`: 「呼び出されるたびに`_isTrue`の現在の値を返す関数」です。`WaitUntil`はこの関数を繰り返し呼び出して、`true`になるタイミングを監視します。
- `cancellationToken: destroyCancellationToken`: このオブジェクトが破棄された場合に、条件が満たされていなくても待機を打ち切るための保険です。これを渡さないと、条件が満たされないままオブジェクトだけ破棄された場合、待機処理が終わらずに残り続けてしまいます。
- `public void OnClicked()`: ボタンに紐付けられたメソッドで、`_isTrue`を`true`に切り替えるだけのシンプルな処理です。

## 実行結果の例
- ボタンを押す前: Consoleには何も表示されません。
- ボタンを押した後: Consoleに「条件が true になりました」と表示されます。

## よくあるつまずきポイント
- `_isTrue = true`にした瞬間に「即座に」`WaitUntil`が反応すると誤解しがちですが、実際には次に条件がチェックされるタイミング（通常は次のフレーム）で待機が終了します。体感ではほぼ同時ですが、仕組みとしては「監視して見つけたら反応する」という流れになっています。
- `cancellationToken`を渡さなくても動作は変わらないように見えるため、「別に付けなくてもいいのでは」と考えてしまいがちです。しかし、条件が二度と満たされないケースを想定できているかどうかが重要で、これを渡し忘れると気づきにくいメモリリークにつながります。
- `WaitUntil`に渡す関数の中でわざと重い処理をしてしまう。条件判定は毎フレーム呼ばれるので、軽い判定にとどめるべきです。
